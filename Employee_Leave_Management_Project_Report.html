Abstract

This project presents the design and implementation of a comprehensive Employee Leave Management System integrated with a complete end-to-end DevOps CI/CD pipeline. The system addresses the real-world challenge of managing employee leave requests through a role-based web application while simultaneously demonstrating modern software engineering and DevOps best practices.

The application provides three distinct user portals — Employee Portal, HR / Manager Portal, and Admin Portal — each with appropriate access control enforced by JSON Web Token (JWT) authentication. Employees can submit, track, and cancel leave requests; managers can review and approve or reject applications; and administrators can manage the employee directory and leave quota configurations.

The back-end is developed using Node.js v20 with the Express.js framework, providing a RESTful API. The system supports dual-database operation: SQLite for zero-configuration local development and MySQL 8.0 for production deployments. The front-end is a responsive Single Page Application built with HTML5, Vanilla CSS3 (glassmorphism dark-mode design), and Vanilla JavaScript.

The DevOps pipeline is orchestrated by Jenkins through a declarative Jenkinsfile comprising seven automated stages: source checkout, dependency installation, automated testing, code quality verification, build verification, health endpoint verification, and a pipeline summary report. Automated testing is implemented with Jest and Supertest, producing JUnit XML reports consumed by Jenkins. Code quality is enforced via SonarQube static analysis.

The application is containerised using Docker with a security-hardened, non-root, Alpine-based image featuring a built-in health check probe. Docker Compose orchestrates the full production stack including the application, MySQL database, Prometheus monitoring scraper, and Grafana dashboards. The application exposes custom business metrics (leave creation, approval, rejection counters) alongside standard system telemetry via the prom-client library.

The project achieves 17 automated test cases with 100% passing rate and demonstrates a fully functional, production-grade CI/CD workflow, making it an ideal capstone for modern DevOps engineering studies.

Keywords: DevOps, CI/CD, Jenkins, Docker, SonarQube, Prometheus, Grafana, Node.js, Express.js, JWT, Leave Management, REST API, Automated Testing, Jest, SQLite, MySQL.

Chapter 1 – Introduction

1.1 Overview

Modern organisations handle hundreds of employee leave requests every month. Manually tracking leave balances, routing approval requests, and maintaining audit trails is error-prone, time-consuming, and difficult to scale. The advent of web-based systems has transformed how leave is managed, but many institutions still deploy these systems without the rigour of modern software delivery practices.

This project presents a Role-Based Employee Leave Management System built not merely as a functional web application but as a complete demonstration of modern DevOps engineering practices. The system integrates the full software development lifecycle — from code authoring and automated testing through containerisation, continuous integration / continuous delivery (CI/CD), to live production monitoring and observability.

The application is accessed through a browser at http://localhost:8080 (or http://localhost:8081 during Jenkins-managed deployments) and is fully functional without any additional configuration, thanks to its built-in SQLite database that activates automatically when MySQL is unavailable. When the full Docker Compose stack is launched, the application connects to a persistent MySQL 8.0 database cluster.

1.2 Problem Statement

Traditional leave management in organisations suffers from several shortcomings:

  • Manual paper-based processes are slow, error-prone, and lack real-time visibility.
  • No role enforcement means any user may inadvertently access privileged operations.
  • Lack of audit trails makes it difficult to trace who approved or rejected a request and when.
  • No observability — system administrators have no insight into application health or throughput.
  • Ad-hoc deployments lead to environment inconsistencies ("it works on my machine" problems).
  • No automated quality gates mean defects reach production undetected.

This project addresses all these issues by combining a purpose-built web application with a production-grade DevOps pipeline.

1.3 Objectives

The key objectives of this project are:

  1. Design and implement a multi-role web application with Employee, HR Manager, and Admin portals.
  2. Implement JWT-based authentication and role-based access control (RBAC) to secure all API endpoints.
  3. Build a RESTful API using Node.js and Express.js with dual database support (SQLite & MySQL).
  4. Write and execute a comprehensive automated test suite (17 test cases using Jest & Supertest) covering authentication, leave workflows, employee management, and DevOps probe endpoints.
  5. Enforce code quality standards using SonarQube static analysis.
  6. Containerise the application using Docker with a security-hardened, non-root Alpine image.
  7. Orchestrate the full production stack using Docker Compose (App + MySQL + Prometheus + Grafana).
  8. Automate the build, test, and verify lifecycle using a 7-stage Jenkins declarative pipeline.
  9. Expose business and system Prometheus metrics and visualise them through Grafana dashboards.

1.4 Scope

The scope of this project includes:

  • A fully functional leave management system with real-time balance tracking across 5 leave categories.
  • Three distinct role-based portals (Employee, Manager/HR, Admin) with enforced access separation.
  • A complete 7-stage automated Jenkins CI/CD pipeline triggered on every code commit.
  • Docker-based portable deployment supporting both local development and production environments.
  • Live telemetry via /health and /metrics endpoints integrated with Prometheus and Grafana.

Chapter 2 – Literature Survey

2.1 DevOps and CI/CD Practices

Kim et al. (2016) in The DevOps Handbook define DevOps as a set of practices that combines software development and IT operations to shorten the system development life cycle while delivering features, fixes, and updates frequently in close alignment with business objectives [1]. The three ways of DevOps — flow, feedback, and continual learning — form the theoretical foundation of this project's pipeline design.

Humble & Farley (2010) introduced the concept of Continuous Delivery [2], establishing that every commit should be a potential release candidate validated by an automated pipeline. This project directly implements this principle through its Jenkins pipeline, which automatically halts deployment if any test fails.

2.2 Jenkins as a CI/CD Orchestrator

Jenkins is an open-source automation server widely adopted in industry for CI/CD pipeline orchestration [3]. Its declarative pipeline syntax, defined in a Jenkinsfile co-located with source code, enables pipeline-as-code — a practice that provides version control and auditability of the build process itself. Several academic studies [4] have confirmed Jenkins as the most commonly used CI tool in enterprise DevOps implementations.

2.3 Docker and Container-Based Deployment

Merkel (2014) introduced Docker as a lightweight alternative to full virtual machine-based deployments [5]. By packaging the application along with its runtime dependencies into a portable image, Docker eliminates environment-specific failures. Best practices such as using Alpine-based images, non-root users, and multi-stage builds — all employed in this project — are documented in the official Docker documentation [6].

2.4 Static Code Analysis with SonarQube

SonarQube provides automated static code analysis to detect bugs, code smells, security vulnerabilities, and duplications. Zampetti et al. (2017) demonstrated that integrating SonarQube into CI pipelines significantly reduces the defect escape rate to production [7]. This project configures SonarQube through a sonar-project.properties file, directing analysis at the src/ directory while excluding generated and static asset files.

2.5 Prometheus and Grafana for Observability

The concept of the "four golden signals" — latency, traffic, errors, and saturation — advocated by the Google SRE Book [8] guides this project's monitoring implementation. Prometheus, a time-series database and monitoring system, scrapes metrics from the application's /metrics endpoint every 5 seconds. Grafana provides the visualisation layer. The prom-client Node.js library is used to expose both standard process metrics and custom business counters (leave requests created, approved, rejected).

2.6 Node.js for REST API Development

Richardson (2013) laid the groundwork for RESTful API design in modern web applications [9]. Node.js, with its event-driven, non-blocking I/O model, is widely used for building high-throughput APIs. Express.js provides the minimalist routing and middleware framework used in this project.

2.7 JWT-Based Authentication

JSON Web Tokens (RFC 7519) provide a compact, self-contained method for securely transmitting information between parties as a JSON object [10]. This project uses JWT with an 8-hour expiry, signed with a configurable secret, to authenticate all API requests. A demo header fallback (x-user-id / x-demo-role) is also supported for laboratory demonstration convenience.

Chapter 3 – System Analysis

3.1 Existing System

Most small and medium-sized organisations manage employee leave through manual processes — paper forms, spreadsheets, or email chains. The drawbacks of such systems include:

  • No real-time leave balance visibility for employees.
  • Slow approval cycles due to manual routing.
  • No audit trail or historical analytics.
  • No system health monitoring or performance metrics.
  • Inconsistent deployments across developer machines and production servers.
  • No automated regression testing to catch defects before release.

3.2 Proposed System

The proposed system eliminates all of the above shortcomings through a modern, integrated approach:

  • Role-Based Web Application — Three distinct portals (Employee, Manager, Admin) with enforced access control.
  • RESTful API — All operations (login, leave submission, approval, employee management) are performed via HTTP APIs.
  • Automated CI/CD Pipeline — Every code change triggers an automated 7-stage Jenkins pipeline.
  • Containerised Deployment — Docker ensures identical environments from developer laptops to production.
  • Live Monitoring — Prometheus scrapes live metrics; Grafana visualises them in real-time dashboards.
  • Quality Gate — SonarQube static analysis prevents low-quality code from being deployed.

5.2.2 Database Abstraction Layer

The database module (src/db/index.js) implements a transparent abstraction that presents a unified query() and execute() interface regardless of the underlying engine. On startup, it attempts to connect to MySQL. If the connection fails, it gracefully falls back to SQLite — making the application work out-of-the-box without any infrastructure setup. 

async function initDb() {
  if (config.DB_TYPE === 'mysql') {
    try {
      mysqlPool = mysql.createPool({ host, port, user, password, database });
      await mysqlPool.getConnection();    // Test connection
      activeEngine = 'mysql';
    } catch (err) {
      console.warn('MySQL failed. Falling back to SQLite.');
      activeEngine = 'sqlite';
      initSqlite();
    }
  } else {
    initSqlite();
  }
  await seedData({ query, execute });    // Seed default users & leave types
}

5.2.3 Authentication Middleware

The authenticate middleware verifies JWT tokens from the Authorization: Bearer <token> header. The requireRole(allowedRoles) middleware factory then enforces RBAC by comparing the authenticated user's role against the allowed roles array. A 403 Forbidden response is returned for insufficient permissions. 

function requireRole(allowedRoles = []) {
  return (req, res, next) => {
    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        success: false,
        message: `Access denied. Required: ${allowedRoles.join(' or ')}`
      });
    }
    next();
  };
}

5.2.4 Leave Business Logic

The leave submission endpoint (POST /api/leaves) implements the following business rules:

  • All four fields (leave type, from date, to date, reason) are mandatory.
  • Days are calculated inclusively: Math.ceil((d2 - d1) / 86400000) + 1.
  • The date range is validated — to_date must be on or after from_date.
  • The leave type ID is validated against the database.
  • On success, a Prometheus counter leave_app_leaves_created_total is incremented with the leave type label.

5.4 Containerisation with Docker

5.4.1 Dockerfile

The Dockerfile uses the lightweight node:20-alpine base image. Key security and production best practices applied:

  • Non-root user — The container runs as the built-in node user, not as root.
  • Production dependencies only — npm ci --omit=dev excludes testing and development packages.
  • Health check — Docker polls http://localhost:8080/health every 20 seconds; 3 failed checks restart the container.
  • Environment variables — NODE_ENV=production and PORT=8080 are set at build time.
FROM node:20-alpine AS base
WORKDIR /app
RUN apk add --no-cache wget curl
COPY package*.json ./
RUN npm ci --omit=dev           # Production deps only
COPY . .
ENV NODE_ENV=production PORT=8080
EXPOSE 8080
HEALTHCHECK --interval=20s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1
USER node                       # Non-root security
CMD ["node", "src/server.js"]

  • APP_NAME = 'employee-leave-management'

  • APP_DIR = 'Employee' — The source directory within the Jenkins workspace
pipeline {
    agent any
    environment {
        APP_NAME = 'employee-leave-management'
        APP_PORT = '8082'

                always { junit allowEmptyResults: true,
                          testResults: "${APP_DIR}/junit.xml" }

        stage('Health Endpoint Verification') { ... } // Stage 6
        stage('Pipeline Summary') { ... }       // Stage 7
    }
}

The critical quality gate is at Stage 3: if any Jest test fails, the pipeline aborts immediately, preventing the build from being verified or deployed. Jenkins captures the JUnit XML test report generated by jest-junit and displays it in the Jenkins build dashboard.

Chapter 6 – Testing

6.1 Testing Strategy

The project adopts an integration testing strategy using Jest as the test runner and Supertest as the HTTP assertion library. Tests run against the real Express application mounted on an in-memory SQLite database, providing fast, isolated, and repeatable execution without any external infrastructure dependency.

The test suite is organised into four test files, each covering a distinct concern:

  • auth.test.js — Login, invalid credentials, and demo user endpoint tests.
  • employees.test.js — Admin CRUD operations and role-based access restriction tests.
  • leaves.test.js — Full leave lifecycle: balance, submit, validate, list, approve, and RBAC tests.
  • health.test.js — DevOps probe endpoints: /health, /metrics, and /api/stats/system.

Tests are executed with npm test, which runs: jest --detectOpenHandles --runInBand --forceExit --reporters=default --reporters=jest-junit. The --runInBand flag ensures sequential execution to prevent database state conflicts between test suites.

7.3 Viva Examination Q&A

Q1: What is the benefit of containerising this application with Docker?

Docker packages the application along with its Node.js v20 runtime, Alpine Linux base, and all production dependencies into a single portable image (approximately 160MB). This eliminates the "it works on my machine" problem and guarantees identical execution across developer laptops, the Jenkins CI server, and the production environment. The non-root user configuration adds a security layer by preventing the application process from escalating privileges inside the container.

Q2: What happens if automated tests fail during the Jenkins pipeline?

The pipeline automatically terminates at Stage 3 (Run Automated Tests). Because subsequent stages — Build Verification, Health Verification, and Pipeline Summary — do not execute, the broken build is never verified or deployed. Jenkins captures the JUnit XML report and marks the build as FAILED in its dashboard. Developers are immediately notified, ensuring that no defective code reaches the production environment.

Q3: How does the monitoring integration work?

The Node.js application uses the prom-client library to expose a /metrics endpoint in Prometheus text exposition format. Prometheus is configured in prometheus.yml to scrape this endpoint every 5 seconds. The metrics include standard Node.js process telemetry (CPU, heap memory, event loop lag) as well as custom business counters for leave requests created, approved, and rejected. Grafana connects to Prometheus as a data source and renders these time-series as dashboards.

Q4: How does Role-Based Access Control (RBAC) work in this system?

Every authenticated request carries a JWT token in the Authorization: Bearer <token> header. The token payload contains the user's role (employee, manager, or admin). The authenticate middleware verifies the token signature, and the requireRole() middleware compares the decoded role against the allowed roles for each endpoint. Attempting to approve a leave request as an employee returns HTTP 403 Forbidden.

Q5: Why does the application support both SQLite and MySQL?

SQLite requires zero external infrastructure — the database is a single file stored inside the application directory. This makes local development and CI pipeline testing instant and dependency-free. MySQL is used in the Docker Compose production stack for its scalability, concurrent connection support (10-connection pool), and data persistence across container lifecycle events. The database abstraction layer in src/db/index.js presents a unified query() and execute() interface to all route handlers, so no business logic changes are needed when switching between the two engines.

Chapter 8 – Conclusion and Future Work

8.1 Conclusion

This project successfully designed, implemented, and demonstrated a full-featured Employee Leave Management System integrated with a production-grade DevOps CI/CD pipeline. The system achieves all stated objectives:

  • A responsive, role-based web application with three distinct portals (Employee, Manager, Admin) enforced by JWT authentication and RBAC middleware.
  • A RESTful API built on Node.js and Express.js serving 18 endpoints, with dual-database support (SQLite for development, MySQL for production).
  • A complete automated test suite of 17 test cases covering authentication, leave lifecycle, employee management, and DevOps probe endpoints — all passing at 100%.
  • A 7-stage Jenkins declarative pipeline that automatically checkouts, installs dependencies, executes tests, verifies code quality, verifies the build, probes the health endpoint, and generates a summary report.
  • A security-hardened Docker container running as a non-root user with a built-in health check probe, orchestrated alongside MySQL, Prometheus, and Grafana via Docker Compose.
  • Live Prometheus metrics including custom business counters and standard Node.js telemetry, visualisable via Grafana dashboards.

The project demonstrates that modern software engineering principles — automation, observability, containerisation, and quality-first development — can be applied even to educational capstone projects, producing systems that reflect real-world industry practices.

8.2 Future Work

The following enhancements are identified for future development:

  1. Email Notifications — Integrate Nodemailer or SendGrid to send automated email notifications to employees when their leave status changes (approved/rejected) and to managers when new requests are submitted.
  2. Kubernetes Deployment — Replace Docker Compose with a Kubernetes deployment manifest (Deployment, Service, ConfigMap, HorizontalPodAutoscaler) to demonstrate container orchestration at scale.
  3. SonarQube Quality Gate Integration — Fully integrate SonarQube scanner into the Jenkins pipeline with a configured quality gate that fails the build if code coverage drops below 80% or critical issues are found.
  4. Holiday Calendar Integration — Integrate a public holiday API to exclude national holidays from leave day calculations automatically.
  5. GitLab CI Integration — Migrate the pipeline definition to a .gitlab-ci.yml for GitLab CI/CD, demonstrating platform portability of CI/CD pipelines.
  6. Grafana Pre-built Dashboards — Ship pre-configured Grafana dashboard JSON files as part of the repository, enabling zero-configuration observability on docker compose up.
  7. Multi-level Approval Workflow — Add a two-tier approval process (Team Lead → HR Director) for long-duration or maternity/paternity leave requests.
  8. Leave Policy Engine — Implement a configurable rules engine that automatically validates leave requests against company policy (e.g., minimum notice period, maximum concurrent leaves per department).
